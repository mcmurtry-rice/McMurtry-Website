# Project Structure

How the McMurtry College website is organized. Read this first if you're new
to the codebase; it explains why files live where they do.

## Top-level layout

```
MurtWebsite/
├── pages/                  Next.js routes. Every .js file here is a URL.
├── components/             React UI components, grouped by section.
├── data/                   ALL site content as JSON — separated from code.
├── lib/                    Shared utilities (Google Sheets, O-Week loader).
├── static/                 Images, PDFs, icons, fonts.
├── scripts/                Maintenance scripts (PDF fixers, etc.).
├── siteimprove/            Siteimprove API fetcher + dashboard scraper.
├── google-apps-scripts/    Google Apps Script source (PCard, McItems, …).
├── docs/                   Build output. Generated by `npm run deploy`.
├── package.json
├── next.config.js
└── README.md
```

## `pages/` — Next.js routes

Each `.js` file under `pages/` is automatically a URL. The router maps file
paths to URLs:

| File | URL |
| --- | --- |
| `pages/index.js` | `/` |
| `pages/about/index.js` | `/about` |
| `pages/about/calendar.js` | `/about/calendar` |
| `pages/oweek/coords.js` | `/oweek/coords` |
| `pages/people/RHAs.js` | `/people/RHAs` |

**Casing matters on the live site.** GitHub Pages is case-sensitive: a file
named `paas.js` produces `/people/paas` and a navbar link to `/people/PAAs`
will 404. When you create a new page, match its filename to the link case.

Pages are thin: they import a section component, wrap it in `Header /
StaggeredMenu / Footer`, and render. They don't contain content logic —
that lives in the components and the JSON files in `data/`.

### Conventions

- **One folder per page-section** — keep co-located. `components/people/court/`
  holds `court.js` and `court.css`. Nothing else goes there.
- **CSS goes next to its JS** — same folder, same base name, imported via
  `./<name>.css` from the component.
- **Globals live in `pages/_app.js`** — every CSS file consumed by the app
  is imported there once. When you add a new component CSS file, add the
  import line to `_app.js` or styles won't apply on first render.
- **Content lives in `data/`, NOT next to the component** — see below.

## `data/` — site content

JSON files containing the actual text/lists/images that render on each page.
Code (`components/`) is a template; `data/` is what fills it in.

```
data/
├── about/        about.json
├── mcm10/        events, faqs, sponsors, mcscottish
├── navigation/   main-navbar, mcm10-navbar, oweek-navbar
├── people/       associates, committees, court, divisionaladvisors,
│                 fellows, mcministry, mcmurtryaffinitygroups, mcteam,
│                 paas, smr, wellbeing
└── resources/    blm, diversityResources, mis
```

Add a new section's content: create `data/<section>/<name>.json`, then
import from the component as `import x from '../../../data/<section>/<name>.json'`.

The 6 Google-Sheets-backed pages (committees, court, fellows, mcministry,
mcmurtryaffinitygroups, paas) keep a JSON copy in `data/people/` as a
fallback schema — the live data comes from Google Sheets via `lib/googleSheets.js`.

## `lib/` — utilities

- **`googleSheets.js`** — fetches a published Google Sheet as CSV, parses
  it, returns rows as objects. Read `lib/googleSheets.README.md` for the
  full API + how to add a new sheet-backed page.
- **`sheets.config.json`** — registry of which Google Sheet (by `gid`)
  feeds which page. Single source of truth.
- **`oweek.js`** — exports the current year's O-Week config, coords list,
  groups, theme, and a path helper for current-year assets. See below.

## How to roll over O-Week each year

This was the single biggest reason the site got reorganized. Now it's
two file operations and zero code changes:

1. **Archive the year that just ended:**
   Copy `static/oweek/current/` → `static/oweek/OLD_O_WEEKS/<year>/`.
2. **Replace `current/` with the new year:**
   Drop new files into `static/oweek/current/` keeping the *same filenames*:
   - `config.json` — countdown date, theme name, PDF filename
   - `coordinators.json` — coord list (names, bios, photo paths, etc.)
   - `groups.json` — O-Week groups
   - `theme.json` — theme paragraphs + subtitle
   - `oweekbook.pdf` — the year's O-Week book
   - `images/coords/`, `images/groups/`, `images/hero/`
3. Build and deploy. The site auto-updates — no JS changes needed.

See `static/oweek/current/README.md` for the exact JSON schemas.

## Build & deploy

| Command | What it does |
| --- | --- |
| `npm run dev` | Local dev server on `:3000` with hot reload. |
| `npm run build` | Production build into `.next/`. Sanity-check before deploying. |
| `npm run deploy` | Build, export to `docs/`, set CNAME, stage for git. |
| `npm run siteimprove:fetch` | Siteimprove REST API fetcher (needs API key). |
| `npm run siteimprove:scrape` | CDP-based dashboard scraper (no API key). |

The live site is GitHub Pages serving `docs/` from `master`. Pushing
`docs/` to GitHub publishes immediately.

## Conventions cheat-sheet

- **Naming:** folders are typically camelCase (`diversityResources`,
  `mcmurtryaffinitygroups`); a few legacy ones use snake_case
  (`financial_inclusivity`). New folders should be camelCase.
- **Imports:** prefer relative paths (`../../../data/people/paas.json`)
  rather than aliased imports — Next.js 9.5 doesn't have path aliases
  configured.
- **Don't edit `docs/`** directly. It's overwritten on every `npm run deploy`.
- **Don't commit `node_modules/`, `.next/`, or `siteimprove/.env`** — they're
  gitignored.
- **Match URL casing exactly** when linking to a page. GitHub Pages is
  case-sensitive.
